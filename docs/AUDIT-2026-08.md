## 🟡 Medium Findings

### M1. `BmiResults.svelte` — Excessive non-null assertions on `tdeeDisplay` and `primePercent`

**Location:** `src/lib/components/BmiResults.svelte` lines 398–401, 468, 478, 486, 491, 496

**Code:**

```svelte
{#if primePercent !== null && primePercent !== 0}
  <span class:badge-above={primePercent! > 0} class:badge-below={primePercent! < 0}>
    {primePercent! > 0 ? '+' : ''}{primePercent!.toFixed(0)}%
  </span>
{/if}

{#if tdeeDisplay}
  ...
  <span>{tdeeDisplay!.bmr}</span>
  <span>{tdeeDisplay!.activityLabel}</span>
  <span>{tdeeDisplay!.deficit500}</span>
  <span>{tdeeDisplay!.tdee}</span>
  <span>{tdeeDisplay!.surplus500}</span>
{/if}
```

**Issue:** Six `!` non-null assertions inside `{#if …}` blocks where the value was just null-checked. Svelte's template type narrowing does not always propagate through `class:` directives and string interpolation, which is why the assertions were added — but they paper over a real narrowing limitation rather than fixing it.

**Risk:** If a future refactor moves the `<span>` outside the `{#if}`, the `!` silently becomes a null deref at runtime. Low immediate risk, but a footgun for future edits.

**Recommended fix (small, safe):**

```svelte
{#if primePercent !== null && primePercent !== 0}
	{@const pp = primePercent}
	<span class:badge-above={pp > 0} class:badge-below={pp < 0}>
		{pp > 0 ? '+' : ''}{pp.toFixed(0)}%
	</span>
{/if}
```

Same pattern for `tdeeDisplay` — bind to a local `{@const td = tdeeDisplay}` inside the `{#if}` block. Eliminates all 6 `!` assertions.

**Effort:** ~10 minutes, mechanical refactor, no behavior change.

### M2. `app.html` inline script — Empty `catch (e) {}` swallows all errors

**Location:** `src/app.html` lines 108–124

**Code:**

```html
<script>
	(function () {
		try {
			var t = localStorage.getItem('bmi.wallpaperTheme');
			var m = {/* … */};
			if (t && m[t]) document.documentElement.style.setProperty('--wallpaper-current', m[t]);
		} catch (e) {}
	})();
</script>
```

**Issue:** The catch swallows every error silently — including `QuotaExceededError`, `SecurityError`, or a `SyntaxError` from a malformed `m` map. In private/incognito mode, `localStorage.getItem` can throw, which is fine to ignore, but the blanket swallow makes future debugging harder.

**Risk:** If the wallpaper map `m` ever drifts out of sync with `page-theme.ts`'s `THEME_URLS`, the silent catch hides the resulting `undefined` lookup. Currently safe (the two are in sync), but a fragility.

**Recommended fix:**

```js
} catch (e) {
  // Best-effort wallpaper preload — failures fall through to default CSS.
  // Intentionally silent: this runs before SvelteKit hydrates.
}
```

Or even better: replace the inline literal `m` map with a `data-theme` lookup so `app.html` and `page-theme.ts` cannot drift.

**Effort:** 5 minutes for the comment, 20 minutes for the data-attribute refactor.

## 🟢 Low Findings

### L1. Direct `localStorage` access in `BmiHistorySparkline.svelte` bypasses storage abstraction

**Location:** `src/lib/components/BmiHistorySparkline.svelte` line 59

```ts
const stored = localStorage.getItem(STORAGE_KEYS.HISTORY);
const history: BMIRecord[] = JSON.parse(stored);
```

**Issue:** Every other consumer goes through `src/lib/utils/storage.ts` (which handles `SecurityError`, `QuotaExceededError`, JSON parse failures, and migration). This component re-implements the read inline.

**Risk:** In private browsing or when storage is disabled, this throws and is caught by the surrounding `try/catch` — so no crash. But the component silently returns empty history instead of triggering the migration path that `storage.ts` provides.

**Recommended fix:** Replace with `loadHistory()` from `storage.ts` (or expose a `getHistoryRaw()` if a snapshot read is intentional for performance).

**Effort:** 15 minutes. Add a test for the sparkline's empty-history path.

### L2. `crypto.ts` direct `localStorage` access for passphrase hint

**Location:** `src/lib/utils/crypto.ts` lines 271, 273, 287

```ts
localStorage.setItem(HINT_KEY, hint.trim());
localStorage.removeItem(HINT_KEY);
return localStorage.getItem(HINT_KEY) || '';
```

**Issue:** The crypto module reads/writes `bmi.passphrase_hint` directly to localStorage instead of going through the `STORAGE_KEYS` registry in `storage.ts`. The key `bmi.passphrase_hint` is not declared in `STORAGE_KEYS` at all.

**Risk:** If `storage.ts` ever migrates keys (as it does for `bmi.history`), the passphrase hint will be orphaned. Also, the hint is stored in **plaintext** in localStorage — this is documented behavior (the hint is intentionally non-secret), but the abstraction leak makes it harder to audit.

**Recommended fix:** Add `PASSPHRASE_HINT: 'bmi.passphrase_hint'` to `STORAGE_KEYS` and use the storage abstraction. No behavior change.

**Effort:** 10 minutes.

### L3. `share.ts` uses deprecated `document.execCommand('copy')` as fallback

**Location:** `src/lib/utils/share.ts` line 108

```ts
const ok = document.execCommand('copy');
```

**Issue:** `execCommand` is deprecated in the spec and removed from some newer browsers. The code correctly prefers `navigator.clipboard.writeText` first and only falls back to `execCommand` when the async clipboard API is unavailable.

**Risk:** Minimal today — every modern browser still supports `execCommand`. The fallback exists specifically for non-HTTPS / older WebView contexts where `navigator.clipboard` is undefined.

**Recommended fix:** Leave as-is. The fallback is intentional and well-documented. Revisit when the Clipboard API achieves >98% browser support (currently ~96% per caniuse).

### L4. Svelte `writable` stores still used in 3 places (not migrated to Svelte 5 runes)

**Location:**

- `src/lib/i18n/index.ts` — locale state
- `src/lib/stores/pwa-update.ts` — service worker update state
- `src/lib/stores/pwa-install.ts` — PWA install prompt state

**Issue:** The codebase has migrated most state to Svelte 5 runes (`$state`, `$derived`, `$effect`), but these three modules still use the legacy `writable` from `svelte/store`. This is **not wrong** — Svelte 5 fully supports stores, and cross-module shared state is a legitimate use case where stores shine. But it's an inconsistency.

**Risk:** None functionally. Svelte 5 supports both patterns. The inconsistency is purely stylistic.

**Recommended fix:** Optional. Migrate to runes if/when these modules are touched for other reasons. Do not migrate just for consistency — stores are idiomatic for module-level shared state.
